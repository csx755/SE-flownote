## 一、MVP 定位

### 1.1 MVP 核心目标

FlowNote 的 MVP 不追求完整知识管理平台，而是验证一个最小但完整的用户价值闭环：

> 碎片便签捕获 → 知识页面结构化 → 任务看板执行 → 用户反馈验证

MVP 的核心假设是：目标用户在学习、项目协作或个人事务处理中，会频繁产生零散想法、资料摘录和待办事项。FlowNote 若能让用户快速记录碎片，并将其转化为可整理的知识页面和可执行任务，就能降低“信息散落、无法沉淀、行动断裂”的痛点。

### 1.2 MVP 成功标准

在 2026年6月13日 22:00 前，系统和材料需要达到以下状态：

- 核心流程可运行：用户能完成注册登录、创建便签、转为知识页面、转为任务、推进任务状态。
- 无重大致命 Bug：系统不崩溃，不丢失核心数据，核心按钮和页面跳转可用。
- 可被真实用户试用：至少 3 名早期用户完成试用并留下原始反馈记录。
- 可被助教快速运行：源码仓库规范，README 和部署说明能指导他人在 10 分钟左右启动系统。
- 有基础工程质量保障：至少覆盖核心 API 或核心流程的基础测试用例。

## 二、需求优先级清单

### 2.1 P0：必须进入 6月13日 MVP

| Feature ID | Feature 名称 | 用户价值 | 最小实现要求 | 验收标准 |
|---|---|---|---|---|
| MVP-001 | 用户注册/登录 | 区分不同用户数据，保证个人内容隔离 | 注册、登录、退出、JWT 鉴权 | 未登录不能访问主页面；登录后只能看到自己的数据 |
| MVP-002 | 便签 CRUD | 快速捕获碎片信息 | 创建、编辑、归档/删除、列表展示 | 用户能在 30 秒内创建并保存一条便签 |
| MVP-003 | 便签时间线 | 降低找回近期记录的成本 | 按创建时间倒序展示，支持基础空状态 | 新便签创建后能立即出现在时间线顶部 |
| MVP-004 | 知识页面 CRUD | 将碎片内容整理为结构化材料 | 新建、编辑、查看、删除知识页面 | 页面标题和正文可保存并再次打开 |
| MVP-005 | Markdown 编辑与预览 | 支持较低成本的结构化表达 | 基础 Markdown 输入和预览；复杂工具栏可后置 | 标题、列表、代码块等基础格式可正常显示 |
| MVP-006 | 便签转知识页面 | 验证“碎片沉淀为知识”的核心价值 | 便签卡片提供“转为知识页面”入口 | 转换后内容完整保留，并跳转到知识页面 |
| MVP-007 | 任务 CRUD | 将信息转化为可执行行动 | 创建、编辑、删除任务 | 任务能被创建并展示在看板中 |
| MVP-008 | 便签转任务 | 验证“碎片驱动行动”的核心价值 | 便签卡片提供“转为任务”入口 | 转换后任务出现在待办列，并保留来源标记 |
| MVP-009 | 任务看板 | 支持任务执行状态管理 | 待办、进行中、已完成三列；支持状态流转 | 用户能将任务从待办推进到已完成 |
| MVP-010 | Docker/本地部署 | 支持快速验收和复现 | Docker Compose 或清晰本地启动步骤 | 他人按文档能启动前端、后端、数据库 |
| MVP-011 | 基础测试 | 防止核心流程回归 | 覆盖认证、便签、知识页面、任务核心逻辑 | 测试命令可运行，关键用例通过 |
| MVP-012 | 验证与反馈报告 | 满足课程提交要求，验证真实价值 | 用户联系信息、原始记录附件、痛点分析、迭代计划 | 至少 3 份真实用户反馈，附件可追溯 |

### 2.3 P2：明确后置到后续版本

| Feature | 后置原因 | 后续版本建议 |
|---|---|---|
| 知识图谱可视化 | 展示价值高，但不是 6月13日核心闭环必需；联调和性能风险较高 | 6月14日后作为 v1.1 重点增强 |

| Markdown 导入导出 | 对早期验证不是刚需 | 反馈中若用户提出迁移需求再优先做 |
| 复杂标签管理页 | 容易变成管理型功能镀金 | 先做基础标签，后续按反馈扩展 |

## 五、核心用户试用设计

### 5.1 试用对象

优先选择以下用户：

- 正在准备课程作业、考试复习或项目管理的学生。
- 平时使用备忘录、Notion、飞书文档、Todo 工具但觉得信息割裂的人。
- 有“临时想法很多，但后续整理和执行困难”痛点的人。

### 5.2 试用任务脚本

每名用户完成以下任务，预计 5-8 分钟：

1. 注册并登录 FlowNote。
2. 创建 2 条便签：一条学习/资料类，一条待办类。
3. 将学习/资料类便签转为知识页面，并补充 Markdown 标题或列表。
4. 将待办类便签转为任务。
5. 在任务看板中将任务从“待办”移动到“进行中”或“已完成”。
6. 回答反馈问题。

### 5.3 反馈问题

- 你平时是否有碎片信息难以整理的问题？请举例。
- 便签转知识页面这个流程是否自然？哪里卡住了？
- 便签转任务是否解决了“记录后忘记行动”的问题？
- 你是否愿意继续使用这个工具？原因是什么？
- 当前 MVP 中最影响使用的 1-2 个问题是什么？
- 你最希望下一版增加什么功能？

### 5.4 反馈材料要求

每条用户反馈至少包含：

- 用户姓名或代号。
- 用户身份，如学生、组长、课程项目成员。
- 可联系信息，如微信、QQ、邮箱或手机号。
- 试用时间。
- 试用设备和浏览器。
- 原始记录附件，如访谈摘要、问卷截图、后台数据截图、用户操作截图。
- 团队分析结论：痛点是否被解决、仍有哪些缺口、下一版如何改。

## 六、工程实践要求

### 6.1 仓库与分支

推荐分支策略：

```text
main
└── develop
    ├── feature/auth
    ├── feature/note
    ├── feature/page
    ├── feature/task
    └── feature/docs-feedback
```

要求：

- `main` 保持可提交版本。
- `develop` 作为日常集成分支。
- 每个核心模块使用独立 feature 分支。
- 提交信息使用 `feat:`、`fix:`、`docs:`、`test:`、`chore:` 前缀。

### 6.2 基础测试要求

MVP 阶段不追求高覆盖率，但必须覆盖最核心风险：

| 测试编号 | 测试内容 | 类型 | 通过标准 |
|---|---|---|---|
| TC-01 | 注册与登录 | API/单元测试 | 正确返回用户信息和 token |
| TC-02 | 便签 CRUD | API/单元测试 | 创建、编辑、归档后状态正确 |
| TC-03 | 便签转知识页面 | API/集成测试 | 页面创建成功，内容一致 |
| TC-04 | 便签转任务 | API/集成测试 | 任务创建成功，来源正确 |
| TC-05 | 任务状态流转 | API/单元测试 | TODO → IN_PROGRESS → DONE 正常 |
| TC-06 | 核心 E2E 主流程 | 手动或自动化 | 用户能完整走通 MVP 闭环 |

### 6.3 Bug 分级

| 等级 | 定义 | 6月13日前处理要求 |
|---|---|---|
| Critical | 系统崩溃、数据丢失、无法登录、安全漏洞 | 必须修复 |
| Major | 便签、知识页面、任务核心流程不可用 | 必须修复 |
| Minor | 非核心功能异常但有替代方案 | 记录并视时间修复 |
| Trivial | UI 细节、文案、轻微样式问题 | 可进入后续迭代 |

## 九、相较原计划的关键调整

原《FlowNote-实现计划.md》面向 6月30日完整 v1.0 版本，功能范围较大。由于课程 MVP 作业要求在 6月13日 22:00 前提交可运行系统和真实用户反馈，本版计划做出以下调整：

- 将截止目标从 6月30日完整 v1.0 调整为 6月13日可验证 MVP。
- 将核心价值聚焦为“便签捕获、知识整理、任务执行”三段闭环。
- 将知识图谱、番茄钟、记忆卡片、Markdown 导入导出等功能后置。
